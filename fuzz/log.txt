# fuzz/log.txt — differential fuzz campaigns (DoD gate 9)
#
# One line per campaign, appended by fuzz/run.sh. A line is only written when
# the harness actually ran: exit code 2 (no node, dead pipe, malformed
# response) writes nothing at all, so an entry here can never mean "the oracle
# never started".
#
# Format:
#   <UTC>  module=<name> seed=<n> cases=<n> ops=<n> wall=<s> divergences=<n>
#
# Reproduce any line exactly:
#   target/release/difffuzz --module <name> --seed <seed> --cases <cases>
#
# A line commented out with `#` is SUPERSEDED, not deleted: it stays readable
# but tests/verify.sh does not count it, so a withdrawn number cannot creep
# back into a total.
#
# `cases` is the case budget rather than the clock, so the replay is not cut
# short on a slower machine. Verified deterministic: seed 7 / 100 cases gives
# ops=20760 on every run, seed 8 gives ops=22096.
#
# ---------------------------------------------------------------------------
# CORRECTION, 2026-08-01 — the two 2026-07-31 lines OVERSTATE their coverage.
#
# `cases` is honest about how many programs were executed, but until the fix
# committed today, almost all of them were the SAME programs.
#
# proptest's TestRunner counts successes for its whole lifetime and loops
# `while successes < config.cases`. The driver reused one runner across
# batches, so every batch after the first executed no new cases at all: it ran
# only the persisted regression corpus, which proptest replays before the (now
# empty) main loop, and then spun. So `cases=16666` was 32 genuinely new
# programs plus two saved seeds re-run ~8,300 times each.
#
# Measured, before the fix: with the corpus file removed, a 120-second campaign
# dropped from 16,666 cases to 32.
#
# The 2026-08-01 lines below are the same two campaigns re-run with a fresh
# runner per batch. The op counts are LOWER (2.84M -> 1.40M) because the
# replayed corpus programs were short and cheap; the coverage is far higher,
# because 4,683 distinct programs replaced 32. Pinned by
# `every_batch_generates_new_cases` in crates/difffuzz/tests/differential.rs.
#
# Note on counting: `cases` still includes the persisted corpus, which proptest
# replays once per batch. That is a few percent of the total and is kept
# deliberately — it guarantees each falsification seed is re-checked
# continuously rather than only when someone remembers to.
#

# GRAMMAR, PER MODULE — including what is deliberately excluded.
#
# DESIGN.md 3.7 asks for narrowed grammars to be disclosed, because "we fuzzed
# it" reads as "we covered everything" when it wasn't.
#
# static-disjoint-set
#   ops          union(x, y) [weight 3] · find(x) · connected(x, y)
#   observed     size · dimension · mapping() · compile()
#                after EVERY op, on both sides
#   ctor sizes   1..=400   — straddles 256, where getPointerArray switches
#                            `parents` to 16-bit while `ranks`, sized from
#                            log2(size), stays 8-bit; and large enough for the
#                            B-7 rank wrap at 256 to be reachable
#   program len  1..600 ops
#   EXCLUDED     out-of-range indices. Upstream reads past a typed array, gets
#                undefined and propagates NaN; the bridge raises a RangeError.
#                That divergence is deliberate and documented (napi module
#                docs, adaptation 3), so fuzzing it would only re-report a
#                known decision. Nothing else is excluded.
#
#   NOTE: mapping() and compile() are observations, not ops. Both call find()
#   on every item, so path compression is exercised on every step of every
#   program rather than when the generator happens to pick it.
#
# sparse-set
#   ops          add(m) [weight 5] · delete(m) [2] · has(m) [2] · clear() [1]
#                $iter("values") [2] · $next() [3] · $spread() [1]
#   observed     size · length · dense · sparse
#                after EVERY op, on both sides. The two backing arrays are
#                public properties upstream, and comparing them slot for slot
#                is what makes the swap-with-last in delete() and the
#                truncating stores checkable directly, rather than only
#                through their eventual effect on iteration order.
#   ctor lengths 0..=400 — 0 included because `new SparseSet(0)` is legal and
#                          every member is then out of range; 400 straddles
#                          256, where getPointerArray switches both arrays to
#                          16-bit and where a truncating dense store starts
#                          folding distinct members onto the same value
#   members      0..length+64, so roughly one in eight is OUT OF RANGE
#   program len  1..200 ops
#   EXCLUDED     NOTHING.
#
#   The exclusion line is the point of contrast with static-disjoint-set.
#   There, out-of-range indices had to be excluded because upstream propagates
#   NaN through arithmetic and the port raises instead. Here every step off the
#   end of the arrays is a well-defined read, a truncating store or a silently
#   dropped store, so the port reproduces it and the fuzzer checks it:
#
#     has(m >= length)    -> false   (undefined < size is false)
#     delete(m >= length) -> false   (undefined >= size is ALSO false, so it
#                                     falls through to dense[undefined] !== m)
#     add(m >= length)    -> corrupts: dense store truncates, sparse store is
#                                     dropped, size++ happens anyway
#
#   and `size` therefore runs past `length`, which is what makes DESIGN.md
#   3.7's `undefined` shrink window reachable THROUGH THE PUBLIC API.
#
#   NOTE: the `$` ops are protocol, not methods (see fuzz/oracle.js). $iter
#   opens the one cursor each side holds; $next steps it against whatever the
#   set has become since, which is the D-08 hybrid capture under test; $spread
#   is Array.from(set), going through the COLLECTION's Symbol.iterator and so
#   constructing a fresh cursor each time. $spread is separate from $next on
#   purpose: the factory half of D-07 is only observable by comparing an op
#   that must restart against one that must not. This is the first grammar in
#   the repo that satisfies D-21's iteration-interleaved-with-mutation
#   requirement; static-disjoint-set had no iterator surface to reach it with.
#
# sparse-map
#   ops          set(m, v) [weight 5] · delete(m) [2] · has(m) [2] · get(m) [2]
#                clear() [1] · $iter("keys"|"values"|"entries") [1 each]
#                $next() [3] · $spread() [1]
#   observed     size · length · dense · sparse · vals
#                after EVERY op, on both sides. `vals` is the one that carries
#                this module: delete() moves the KEY into the hole and leaves
#                the VALUE where it was (B-11), so a port that "tidied that up"
#                would still agree on size, dense, sparse and every has() --
#                and disagree only on get() and on vals itself.
#   ctor         BOTH upstream signatures, four value stores:
#                  new SparseMap(length)                  -> Array
#                  new SparseMap(Uint8Array,  length)     -> 8-bit
#                  new SparseMap(Uint16Array, length)     -> 16-bit
#                  new SparseMap(Uint32Array, length)     -> 32-bit
#                A constructor cannot travel over JSON, so the Rust side sends
#                {"$global": "Uint8Array"} and fuzz/oracle.js resolves it
#                against the real global -- deliberately only for `init` ctor
#                arguments, never for an op's.
#   lengths      0..=400, as sparse-set, and for the same two reasons
#   members      0..length+64, so roughly one in eight is OUT OF RANGE
#   values       0..=1000, so an 8-bit value store truncates often
#   program len  1..200 ops
#   EXCLUDED     the op alphabet, nothing. The VALUES are integers, which is
#                narrower than every JS number: the bridge takes f64, this spec
#                takes u32, because the oracle compares JSON and a float that
#                renders 13.0 on one side and 13 on the other is a false
#                divergence rather than a finding. Disclosed here rather than
#                left implicit.
#
#   Why all three iterator factories are generated. Once size has run past
#   length the three projections DISAGREE, and that is exactly where a port
#   goes wrong: keys() gaps on dense, values() may still have real data from an
#   Array store that grew past the map's length, and entries() never gaps at
#   all -- upstream builds the pair [dense[i], vals[i]] and yields the ARRAY,
#   so a missing half is `undefined` inside a yielded value. $spread goes
#   through the collection's Symbol.iterator, which upstream aliases to
#   entries() rather than values().
#
# sparse-queue-set
#   ops          enqueue(m) [weight 4] · dequeue() [3] · has(m) [3]
#                clear() [1] · $iter("values") [2] · $next() [3] · $spread() [1]
#   observed     size · capacity · START · dense · sparse
#                after EVERY op, on both sides. `start` is the one this module
#                adds over its siblings and it earns its place: falsification B
#                below differs in NOTHING ELSE -- same size, same members, both
#                backing arrays identical -- so without `start` observed it
#                would have gone undetected.
#   ctor         a mixture rather than one range, because the interesting
#                capacities are not uniformly distributed:
#                  0..=400  [weight 4]  the ordinary range, 0 included because
#                                       `new SparseQueueSet(0)` is legal and
#                                       makes every index computation NaN (B-14)
#                  1..=8    [weight 3]  small rings, where a 200-op program
#                                       wraps many times instead of filling once
#                  {255,256}[weight 2]  the B-12 boundary and its control. 256
#                                       is a POINT, not a range: a uniform draw
#                                       over 0..=400 reaches it about once in
#                                       400 programs.
#   members      0..capacity+64, so roughly one in eight is OUT OF RANGE
#   program len  1..200 ops
#   EXCLUDED     capacity 65536, the SECOND B-12 boundary. It is the same defect
#                one width up and it is covered by a native test
#                (`the_sentinel_truncates_at_the_second_boundary_too`) instead.
#                Including it cost about 95% of this campaign's throughput --
#                MEASURED, 880 op/s against 15,000 -- because the observable
#                state is two backing arrays, serialised, sent and compared
#                after every single operation. A 60-second campaign executing 5%
#                of the programs is a worse check than a native test plus a fast
#                campaign. Nothing else is excluded; every out-of-range member
#                is generated.
#
#   Why dequeue is weighted at 3. It is the only op that moves `start`, and the
#   ring is what this module has that its siblings do not. A read-heavy mix
#   would fill the ring once and never rotate it.
#
#   The B-12 sentinel needs no special op to observe: `sparse` is in the
#   observed state, so every dequeue compares the value written into it.
# hashed-array-tree
#   ops          push(v) [5] . pop() [3] . set(i, v) [3] . get(i) [3]
#                grow(c) [1] . grow() [1] . resize(l) [2]
#   observed     length . capacity . blockSize . offsetMask . blockMask . blocks
#                after EVERY op, on both sides. `blocks` is every block, slot
#                for slot -- which is what makes the truncating stores, the
#                set(length) write and "a shrinking resize deallocates nothing"
#                checkable directly rather than only through their effect on
#                get().
#   ctors        Uint8Array/Uint16Array/Uint32Array x blockSize {1,2,4,8}
#                x initialLength 0..24 x initialCapacity 0..24
#   indices      0..64 against lengths that rarely exceed 30
#   values       0..320, above 255 so a Uint8Array tree truncates
#   program len  1..200 ops
#   EXCLUDED     non-integer arguments, and blockSize outside {1,2,4,8}.
#                Nothing else -- out-of-bounds indices are generated freely.
#
#   Block sizes are TINY on purpose. Upstream's own test uses the 1024-element
#   default and never leaves its first block, which is precisely why its pop
#   bug (B-11) survives there. At blockSize 2 a 200-op program is almost
#   entirely cross-block.
#
#   NOTE: this is the first module whose operations legitimately THROW, which
#   is the case spec::CheckFailure's "Trap for the next module" note
#   anticipated. fuzz/oracle.js now catches an exception thrown BY AN OPERATION
#   and reports {"$throw": "<message>"}, compared like any other result --
#   by its FULL TEXT, which ties these campaigns to Node 24.18.1 for the
#   V8-worded TypeError. Previously such a throw arrived as OracleError and
#   would have aborted the campaign instead of being reported.
#
# bit-set
#   ops          set(i) [4] . set(i, 0) [2] . reset(i) [3] . flip(i) [2]
#                get(i) [2] . test(i) [1] . rank(i) [2] . select(r) [2]
#                clear() [1] . $iter("values") [1] . $iter("entries") [1]
#                $next() [3] . $spread() [1]
#   observed     size . length . array . toJSON()
#                after EVERY op. `array` is the point: `size` alone would agree
#                in plenty of programs where the words had already diverged.
#   ctor lengths 0..=400 -- thirteen words. 0 included because new BitSet(0)
#                allocates nothing at all; 400 is sparse enough that empty
#                words between set bits are routine, which is what B-14 needs.
#   indices      0..length+64, so a steady fraction land in B-19's band (past
#                `length` but inside the last allocated word) and beyond it
#   program len  1..200 ops
#   EXCLUDED     NOTHING.
#
#   `reset` is weighted UP rather than down. B-13 only misfires on a bit that
#   is ALREADY clear, so a low weight would make the interesting case rare
#   rather than routine.
#
#   $iter alternates values/entries: they share an implementation in this port
#   and are separate closures upstream, so fuzzing one would leave the other
#   unchecked. clear() is in the alphabet BECAUSE it interacts with an open
#   cursor -- it replaces this.array, and a cursor opened beforehand must keep
#   reading the pre-clear words.
#
# bit-vector
#   ops          set(i) [3] . set(i, 0) [2] . reset(i) [3] . flip(i) [2]
#                get(i) [2] . test(i) [1] . rank(i) [2] . select(r) [2]
#                push(1) [3] . push(0) [3] . pop() [3]
#                resize(l) [2] . reallocate(c) [2] . grow(c) [1] . grow() [1]
#                $iter("values") [1] . $iter("entries") [1] . $next() [3]
#                $spread() [1]
#   observed     size . length . capacity . array . toJSON()   after EVERY op
#   ctor lengths 0..=200 . indices 0..length+64 . extents 0..512
#   program len  1..200 ops
#   EXCLUDED     CUSTOM GROWTH POLICIES.
#
#   Upstream's policy is a JS function and a generated program is JSON, so the
#   default policy is the only one fuzzed. Because the default is strictly
#   increasing, BOTH THROWS IN applyPolicy ARE UNREACHABLE from this grammar.
#   They are covered by native tests in mnemonist-core instead
#   (a_policy_can_fail_three_ways, a_non_integer_policy_result_is_rounded_up).
#   Recorded here rather than left implicit: a silently narrowed grammar reads
#   as "we covered everything" when it did not.
#
#   push(1) and push(0) are separate ops because only the former touches `size`
#   and only the latter leaves a stale bit, and B-17 needs both interleaved
#   with pop(). `set` is the only op here that throws.
# stack
#   ops          push(v) [weight 6] · pop() [3] · peek() [2] · clear() [2]
#                $iter("values") [2] · $next() [4] · $spread() [1]
#   observed     size · items · toArray()
#                after EVERY op, on both sides. `items` is a public property
#                upstream, and observing it directly is what makes the
#                ARRAY-REBINDING of clear() checkable without waiting for a
#                cursor to notice. size and items.length are separate
#                quantities upstream (D-19); comparing both is how a port that
#                silently unified them would be caught.
#   values       0..48, small enough that duplicates are frequent -- a stack is
#                not a set, and a port that deduplicated is only caught by
#                repeats
#   program len  1..200 ops
#   EXCLUDED     NOTHING. Every method stack.js exposes is in the alphabet or
#                the observation set, except inspect(), which is not ported.
#
#   THE POINT OF THIS GRAMMAR IS A PAIR OF MUTATIONS THAT MUST DIFFER.
#   clear() is `this.items = []` -- a NEW array -- so a cursor opened
#   beforehand keeps walking the old one and is unaffected. pop() shortens the
#   SAME array, so a cursor opened beforehand reads past its new end and yields
#   undefined. A port backing `items` with a Vec<T> produces identical (wrong)
#   answers for both, and no upstream test notices, because test/stack.js never
#   mutates between opening a cursor and draining it. That is why clear()
#   carries real weight here rather than being a token op.
#
# queue
#   ops          enqueue(v) [weight 6] · dequeue() [4] · peek() [2] · clear() [1]
#                $iter("values") [2] · $next() [4] · $spread() [1]
#   observed     size · offset · items · toArray()
#                after EVERY op, on both sides. offset and items are the point:
#                toArray() alone cannot tell a compacted queue from an
#                uncompacted one holding the same elements, so a port could get
#                the whole compaction schedule wrong for an entire program with
#                nothing noticing.
#   values       0..48
#   program len  1..200 ops
#   EXCLUDED     NOTHING.
#
#   dequeue is weighted heavily because the compaction only fires on a dequeue
#   and `++offset * 2 >= items.length` needs several in a row to be
#   interesting. $next outweighs $iter four to one so cursors are stepped
#   repeatedly with enqueues and compactions landing between the steps.
#
#   THE STEP-AFTER-EXHAUSTION CASE IS A BEHAVIOUR HERE, NOT A CORNER.
#   Queue.prototype.values re-reads items.length on EVERY step where
#   Stack.prototype.values freezes it, four files away in otherwise identical
#   code, and obliterator's Iterator has no done flag -- so a queue cursor that
#   has already reported {done: true} RESUMES when the queue grows. Core
#   expresses that as Sequence::limit (D-42).
#

# $forEach — THE OP THAT WAS MISSING, ADDED 2026-08-01 AFTER B-31.
#
# Appended rather than folded into the eight module blocks above, so nothing
# already written here moves.
#
# WHAT WAS WRONG WITH THE GRAMMARS ABOVE
#
# Every module block above discloses what it excludes, and none of them
# disclosed this: no module's alphabet contained `forEach` at all. sparse-set
# had $iter/$next/$spread interleaved with mutation and therefore satisfied
# D-21, so the omission read as coverage. It was not. B-31 -- a JS callback
# mutating the collection it is walking -- is reachable ONLY through forEach,
# and 2.94M operations could not express a single program that tried. An
# alphabet that omits a method omits every bug reachable only through it.
#
# THE OP
#
#   $forEach(method, rule, limit)
#
#   Walks the instance and, from inside the callback, calls one of its own
#   mutating methods. `method` is null for a plain walk; `rule` says how that
#   method's arguments come out of the callback's own; `limit` is how many
#   times it may fire. The compared RESULT is {"seen": [[a0, a1], ...]} -- the
#   callback's argument pairs, so the walk's shape is compared and not only
#   the state it leaves behind. Observable state is still compared after the
#   op, as for every other op.
#
#   Rules:  none · arg0 · arg0+1 · arg1 · arg1,arg0
#   Limits: 1 (the classic "mutate on the first step, then keep walking") and
#           the per-mutation "every step" cap. Both are generated; neither
#           subsumes the other.
#
# PER MODULE — (method, rule, every-step limit)
#
#   sparse-set        delete/arg0/every · add/arg0+1/2 · clear/none/every
#   sparse-map        delete/arg1/every · set/arg1,arg0/every · clear/none/every
#   sparse-queue-set  dequeue/none/every · enqueue/arg0+1/every · clear/none/every
#   bit-set           set/arg1/every · reset/arg1/every · flip/arg1/every
#                     clear/none/every
#   bit-vector        set/arg1/every · reset/arg1/every · flip/arg1/every
#                     push/none/4 · pop/none/every
#   stack             pop/none/every · push/arg0/every · clear/none/every
#   queue             dequeue/none/every · enqueue/arg0/every · clear/none/every
#   default-map       delete/arg1/every · set/arg1,arg0/every · clear/none/every
#
#   The caps are not tuning. sparse-set's forEach bound is LIVE, so an
#   uncapped `s.forEach(m => s.add(m + 1))` never terminates -- upstream
#   included -- and the cap is what makes the op well-defined rather than what
#   makes it fast. bit-vector's push cap of 4 IS tuning, and is stated as
#   such: a push per bit over a 400-bit vector is hundreds of reallocations
#   per case, and the throughput buys more programs than the depth does.
#
#   What this op puts under test is the LOOP SHAPE, and upstream is
#   deliberately inconsistent about it: sparse-set and sparse-map re-read
#   `this.size` every iteration, sparse-queue-set/stack/queue capture their
#   bound before the first step, bit-set/bit-vector snapshot each word, and
#   default-map's is a live `Map` walk that visits entries added during it.
#   Seven modules, four different answers, and no program the old alphabets
#   could generate distinguished any of them.
#
# EXCLUDED, and it is a real narrowing
#
#   A selected callback argument that is `undefined` SKIPS the mutation, on
#   both sides. Passing it on is legal JavaScript and does something specific:
#   `this.sparse[undefined]` is `undefined`, `undefined >= size` is false, and
#   upstream falls through into a swap indexed by `undefined` -- a silently
#   discarded expando write on a typed array, plus a `size--`. `usize` cannot
#   carry that and mnemonist-core does not model it. The plain ops still
#   generate every out-of-range member, so the corrupted regime itself is not
#   excluded; only the specific act of feeding an `undefined` back in is.
#
# WHAT $forEach DOES *NOT* REACH, AND THIS IS THE IMPORTANT LINE
#
#   B-31 itself. This fuzzer compares mnemonist-core against upstream JS. The
#   napi bridge -- where the `noalias readonly` hoist actually happened -- is
#   not in that loop at all, so no op alphabet, however complete, can catch
#   that class of bug here. The specs that DO catch it are
#   tests/boundary/reentrancy.js, which drive the real addon with real JS
#   callbacks; they were red on seven cases against the pre-fix bridges and
#   green after. Recorded here so that "we added a forEach op" is never read
#   as "B-31 is now fuzz-covered".
#
# FALSIFIED, like everything else here
#
#   Freezing the live `this.size` bound in SparseSetSpec's $forEach arm turned
#   a campaign red in 0.7s. See the commented seed=777 line below.
#
# ---------------------------------------------------------------------------
# THE FUZZER WAS FALSIFIED BEFORE IT WAS TRUSTED.
#
# Gate 6's lesson applies to the fuzzer itself: one that has never been seen to
# catch anything is just a second green light. The sabotage was to *fix*
# upstream's B-7 rank bug in the core, making the port strictly more correct
# than upstream and therefore wrong, since the elected root is observable
# through find(). Caught in 129 cases (0.3s), shrunk from 600 ops to three.
# Reverted; the seed is committed in
# crates/difffuzz/proptest-regressions/static-disjoint-set.txt with a
# provenance header, and proptest replays it before any novel case below.
#
# sparse-set was falsified twice, one sabotage per half of its grammar, both
# reverted and both seeds committed with provenance in
# crates/difffuzz/proptest-regressions/sparse-set.txt:
#
#   A. `delete`'s two swap stores treated as if they behaved alike past
#      capacity, i.e. writing sparse[0] where upstream writes a string-keyed
#      expando that leaves the array untouched. This is the mistake the port
#      actually made first. Caught in 1,416 cases (6.6s), shrunk to 7 ops.
#      It proves the out-of-range half of the grammar is doing work.
#
#   B. The shrink window collapsed -- `Step::Gap` returned as `Step::Done`,
#      which is exactly DESIGN.md 3.7's rejected Option B. Caught in 352 cases
#      (0.3s), shrunk to TWO operations:
#          var s = new SparseSet(0); s.add(0); Array.from(s);
#          port []   upstream [undefined]
#      It proves the cursor half of the grammar is doing work, and it corrects
#      a measurement in DESIGN.md 3.7: Option B costs zero on the 40% axis
#      because no upstream TEST reaches it, but it is reachable from the
#      public API in two calls and the fuzzer sees it immediately.
#
# sparse-map was falsified twice as well, one sabotage per half of its NEW
# grammar -- the value store and the projections -- both reverted and both
# seeds committed with provenance in
# crates/difffuzz/proptest-regressions/sparse-map.txt:
#
#   A. `delete` "fixed" to move the value along with the key, i.e. B-11
#      repaired. Caught in 1,474 cases (3.0s), shrunk to three ops:
#          var s = new SparseMap(5); s.set(0,0); s.set(1,1); s.delete(0);
#          port vals [1,1,...]   upstream [0,1,...]
#      This is the most instructive seed in the repo: the SAME sabotage leaves
#      the upstream mocha suite at 9 passing / 0 failing, because that file
#      only ever deletes from a one-element map, where the swap is a
#      self-assignment. Measured both ways -- see docs/modules/sparse-map.md.
#
#   B. The `Array` value store made unable to grow, i.e. given the typed
#      store's behaviour. That is the natural Rust assumption: a Vec allocated
#      at `length` has a length. Caught in 1,147 cases (4.6s), shrunk to ONE
#      operation:
#          var s = new SparseMap(0); s.set(0, 0);
#          port vals []   upstream [0]
#      It proves the store half of the grammar is doing work, and it is why
#      the ctor strategy generates all four value constructors rather than the
#      one the upstream test file happens to use.
#
# sparse-queue-set was falsified twice, once per half of its new grammar -- the
# ring and the degenerate capacity -- both reverted, both seeds committed with
# provenance in crates/difffuzz/proptest-regressions/sparse-queue-set.txt:
#
#   A. `enqueue` "fixed" to refuse a full ring, i.e. B-13 repaired. Caught in
#      811 cases (0.8s), shrunk to two ops on the smallest possible ring:
#          var s = new SparseQueueSet(1); s.enqueue(0); s.enqueue(1);
#          port dense [0] size 1   upstream dense [1] size 2
#      As with sparse-map's A, the same sabotage leaves the upstream mocha
