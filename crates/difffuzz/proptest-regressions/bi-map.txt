# PROVENANCE

# Both entries are REAL divergences BUG-BI-MAP-1 found — the port was, at the time
# each was caught, more correct than upstream, which this project treats as a
# defect. Both were fixed; the campaign is clean on the fixed tree (5,000
# cases / 38.3s, seed 42, zero divergences). See docs/modules/bi-map.md.
#
#   1  `new BiMap(); s.set("a","a"); s.clear();` -- upstream's shared `clear`
#      body (`this.size = 0; this.items.clear(); this.inverse.items.clear();`)
#      resets only ONE counter, leaving `inverse.size` at its pre-clear value
#      (1) while the underlying maps are genuinely empty. The first port of
#      `BiMap::clear` derived both `size()`/`inverse_size()` from
#      `OrderedMap::len()`, so it "healed" the desync immediately and reported
#      `inverse_size() == 0` — more correct than upstream. Caught in 18 cases
#      (0.3s). Fixed by giving `BiMap` two real stored counters and having
#      `clear`/`clear_reverse` reset only the matching one.
#
#   2  The same program plus `s.delete("a")`. Fixing (1) by unconditionally
#      resyncing both counters from the live maps on every `set`/`delete` call
#      reintroduced the same bug one op later: `delete` on an absent key is a
#      no-op upstream (`del` returns `false` without touching either counter),
#      but recomputing from `.len()` regardless of whether anything was
#      deleted "healed" the still-stale `inverse_size` early. Caught in 177
#      cases (0.3s) on the very next campaign run. Fixed by resyncing only on
#      `Some(_)` (a real deletion).
#
