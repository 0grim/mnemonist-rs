# PROVENANCE OF THE ENTRY BELOW -- this one recorded a real port defect, found
# by this grammar's very first campaign, before any 60-second run had ever
# been logged.
#
# `LruCache::for_each_walk` (née: a `Sequence`/`CursorState` walk reused for
# `forEach`) advanced its internal pointer to `forward[pointer]` BEFORE the
# `$forEach` mutation for that step ran, where upstream's own loop body reads
# `forward[pointer]` textually AFTER its callback returns:
#
#     while (i < l) {
#       callback.call(scope, values[pointer], keys[pointer], this);
#       pointer = forward[pointer];   // <-- after, not before
#       i++;
#     }
#
# So a `forEach` callback that promotes (`set`s an existing key, which splays
# it to the front) the pointer the walk was about to visit next observed a
# DIFFERENT successor than upstream did, because the port had already
# captured the old one. Confirmed at op #5 of the program below:
# `$forEach("set", "arg1,arg0", 1000000)` re-promotes each visited entry as it
# is walked, and the third callback invocation disagreed -- port saw
# `[undefined, 1]`, upstream re-saw `["w", true]`.
#
# Fixed by `ForEachWalk` (`crates/mnemonist-core/src/structures/lru_cache.rs`),
# which gives the caller `current()`/`advance()` as two separate calls instead
# of one `Sequence::slot()` that does both — see that type's doc comment, and
# `docs/modules/lru-cache.md`'s "Bugs this found". The bridge's own
# `for_each_entries` (`crates/mnemonist-napi/src/lru_cache.rs`) had the
# identical bug, invisible to `test/lru-cache.js`, which never mutates from
# inside a `forEach` callback; fixed there too, in the same commit.
#
# This seed now passes. It stays checked in as a regression guard, and
# proptest replays it before any novel case.
